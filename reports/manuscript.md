# CHAPTER 1: INTRODUCTION
## 1.1 General Introduction
CLOAK is a desktop application for encrypted text communication between two peers on a local network. Its interface uses Python’s Tkinter toolkit, with standard widgets and Canvas controls [1]. The application combines discovery, connection management, password verification, message encryption, and a conversation view. A user supplies a callsign and a private passphrase, finds another running client, and establishes a channel before sending text. The project is intended for an Advanced Programming Practice demonstration of modular application design.

The networking layer uses Python sockets [2]. UDP advertisements help clients find each other, while TCP carries framed messages. The revised design separates the graphical interface from the secure session and transport layers. Worker threads perform network operations [3]; a synchronized queue carries results to the interface [4]. This arrangement lets the application remain responsive while a connection is being established or a password-derived key is computed.

The project concerns the Python implementation in this directory. A separate C++ report in the parent repository does not describe this application. Features such as a Signal-style ratchet, internet relay, persistent encrypted database, group chat, and public-key identity verification are therefore not claimed. This distinction keeps the report aligned with the implemented system and the evidence collected during testing.
---PAGE---
## 1.2 Problem Definition
A small desktop chat application must solve more than the delivery of a text string. It must identify reachable endpoints, distinguish a TCP connection from a usable encrypted session, maintain consistent interface states, and recover when the other participant leaves. An application that enables Send immediately after opening a socket can give a misleading impression of readiness. If the users entered different passwords, the failure may become apparent only after their first message is lost.

The initial Python application already provided a useful modular starting point, but its readiness indicator preceded password confirmation. Preset names also bypassed setup, leaving the passphrase unset. Its disconnect path did not consistently restore the connection controls. These behaviors affected the demonstration workflow even when the underlying encryption routine worked correctly. The task was consequently treated as both an interaction-design exercise and a session-lifecycle repair.

The resulting problem statement is to provide a clear, recoverable workflow for one-to-one encrypted LAN messaging using Python and Tkinter. Users must be told when a connection is pending, when the shared password has been verified, when sending is possible, and when they need to reconnect. Discovery failure must have an alternative path. Error handling must return control to the user instead of leaving the application apparently connected or permanently disabled.
---PAGE---
## 1.3 Motivation
The motivation is to make networking and cryptography visible through an approachable desktop workflow. A command-line encryption demonstration proves a narrow transformation from plaintext to ciphertext and back, but it does not expose the practical coordination required by two independent programs. Adding discovery, framing, password verification, and connection recovery creates a more complete programming exercise. Each feature has a distinct responsibility that can be inspected and tested.

A local peer-to-peer architecture also reduces the number of components needed for a classroom demonstration. There is no application account service or message relay to deploy. Both participants run the client and exchange messages directly, subject to the local network’s rules. This convenience must be described carefully: direct communication does not make endpoints trustworthy, conceal network metadata, or provide internet reachability. It simply removes a central application server from this specific workflow.

## 1.4 Objectives And Acceptance Criteria
The first objective is a dependable startup flow. Every supported launcher must request a nonempty passphrase and a callsign of one to sixty-four characters. A supplied command-line name should prefill the field rather than bypass it. The second objective is reliable peer access through automatic discovery and a direct IPv4 address and TCP port. A user must have a practical route forward when broadcast discovery is unavailable.

The third objective is truthful connection state. A new session must exchange protocol information and prove possession of the shared password before either interface allows ordinary messaging. Wrong passwords and incomplete handshakes must fail with a useful explanation. The fourth objective is reversible lifecycle behavior: users must be able to disconnect, return to the offline state, and start another session without restarting the application.

The final objectives concern maintainability and evidence. Network callbacks should not manipulate widgets directly. Malformed input should close a connection cleanly. Automated tests should exercise both successful and unsuccessful sessions, while a live GUI check should cover setup, message exchange, and reconnection. The documentation must identify what was actually tested and separate local-machine evidence from an unperformed two-device LAN test. The report should describe the final Python architecture and record the three team members and the supplied academic details accurately.
---PAGE---
## 1.5 Scope And Operational Boundaries
CLOAK supports one active conversation per application instance. Both peers share a private passphrase and run compatible versions of the Python client. They communicate using IPv4 on a network that permits the relevant traffic. The default discovery port is UDP 5000; the default listening port is TCP 5001. Two instances on one machine require different TCP ports, which the convenience launchers provide. Direct connection is useful for local testing and for networks where broadcasts are filtered.

The application transfers text rather than files. Conversation history is displayed in memory and is not deliberately written to an application database. There is no offline mailbox, message synchronization, typing indicator, group membership protocol, or delivery receipt. A successful socket write is displayed as a local outgoing message; it is not proof that the remote user has read the text. The packet counter measures application-level message activity rather than physical network packets.

## 1.6 Sustainable Development Goal And Responsible Use
The project has a limited educational connection to Sustainable Development Goal 9, which concerns industry, innovation, and infrastructure [5]. Building and testing a local communication tool develops practical skills in software infrastructure, modular design, and secure data handling. The relevant contribution is learning and experimentation rather than a measured social or economic outcome. The project does not claim to increase network access or satisfy a particular United Nations target by itself.

A direct LAN demonstration can operate without an application cloud account or an external chat server. This may be convenient in teaching environments with restricted internet availability, provided Python, Tkinter, and the required packages are already installed. The application still relies on functioning devices and local network infrastructure. Installation may require internet access, and institutional firewalls can prevent either discovery or direct TCP communication. These dependencies should be acknowledged when planning a demonstration.

Responsible use also requires accurate explanations of confidentiality. Students should choose a strong, private passphrase and exchange it through an appropriate separate channel. They should avoid real sensitive information during demonstrations, because screenshots and shared displays can reveal message contents even when network traffic is encrypted. The project’s SDG discussion is therefore grounded in technical education and transparent communication of limitations, rather than broad claims about environmental savings or societal security improvements that were not evaluated.

# CHAPTER 2: SYSTEM REQUIREMENTS
## 2.1 Hardware Requirements
The application requires two running Python processes and a graphical desktop for an interactive demonstration. These processes may run on separate computers on the same local network, or on one computer using distinct listening ports. A keyboard and pointing device support normal interaction; the custom action controls also accept keyboard activation. A display capable of showing the minimum 940 by 760 client area is required for the revised layout. Smaller displays have not been validated.

No dedicated server, graphics accelerator, microphone, or camera is required. CPU work is concentrated in password-based key derivation and ordinary application processing. The revised derivation uses 1,200,000 PBKDF2 iterations, so connection preparation takes more work than a simple socket connection. It runs on a worker thread to preserve responsiveness. A universal minimum CPU frequency or memory size is not asserted because no systematic hardware benchmark was performed.

For a two-device demonstration, both computers need a reachable IPv4 interface. Wi-Fi client isolation, separate VLANs, operating-system firewalls, and VPN routing can affect connectivity. A cable or wireless link alone is insufficient evidence that the clients can reach each other. The demonstration procedure should check the displayed local endpoint, listening port, and network permissions. Localhost testing remains valuable for validating application behavior, but it does not replace a real two-device check of the surrounding network infrastructure.
---PAGE---
## 2.2 Software Requirements
The runtime uses Python, Tkinter/ttk, and the cryptography package. Tkinter supplies the graphical interface; standard-library modules provide sockets, threads, queues, JSON serialization, binary packing, timing, argument parsing, and random secret generation. JSON encodes the message envelope [6], while the struct module encodes its fixed-width length header [7]. Fernet supplies authenticated symmetric encryption [8], and PBKDF2HMAC derives keys from the shared passphrase [9].

The code uses modern Python annotations, including union syntax, so Python 3.10 or later is the documented baseline. The available development environment was inspected directly: it contains Python 3.15.2, Tk 9.1, and cryptography 50.0.2. Those version observations describe the tested machine rather than a claim that all other supported operating systems and versions have been verified. On Linux, Tkinter may require an operating-system package in addition to Python itself.

Report generation is separate from application execution. The Python document builder uses python-docx [10], Pillow for diagram assets, and ReportLab for the companion PDF. These tools are not GUI dependencies of CLOAK. Keeping runtime and report requirements separate avoids making a user install document-production packages just to chat. The project includes reproducible commands for the application, headless tests, live GUI checks, and report generation, with generated artifacts placed in the reports directory.
---PAGE---
## 2.3 Functional Requirements
A user must be able to enter a callsign and passphrase, reveal or hide the passphrase during setup, and enter the main interface only after the required fields are valid. The client must listen for incoming TCP sessions and announce its endpoint through periodic UDP discovery. Discovered peers must appear with a name, address, and port. Stale advertisements must eventually disappear, while selecting a peer should remain stable across ordinary list refreshes.

A user must be able to connect through a selected advertisement or a manually entered IPv4 endpoint. The interface must distinguish connection preparation from a verified conversation. The session must reject incompatible protocol messages, malformed handshakes, and incorrect password proofs. Ordinary chat controls must remain disabled until verification succeeds. The user must be able to disconnect voluntarily, and an unexpected remote termination must restore an offline interface.

Once connected, the client must encrypt outgoing text, decrypt and authenticate incoming text, and display the two participants’ messages distinctly. Empty composer input must not create a message. The GUI limits outgoing messages to 64 KiB of UTF-8 text, while the transport caps framed envelopes at 1 MiB. Failures should be visible in the conversation/status area. Closing the application must stop discovery, release the listener, close the session, and cancel scheduled interface callbacks.

## 2.4 Nonfunctional Requirements And Constraints
Responsiveness is a primary nonfunctional requirement. Network waits, password derivation, and socket writes should run outside the Tkinter event loop. The main thread should perform short widget updates and bounded queue polling. This is consistent with Python’s documentation of Tkinter’s event-driven execution model [1]. The design does not attempt real-time guarantees; the relevant expectation is that normal connection operations do not freeze the interface.

Robustness requires explicit limits and recoverable state changes. Invalid frame lengths must be rejected before the client allocates an arbitrarily large payload. Invalid JSON or unexpected envelope shapes should terminate the affected connection cleanly. A stale event from an old session must not reset a new conversation. A second incoming connection should be refused while the application is already connecting or connected. These rules reduce inconsistent behavior during repeated demonstrations.

## 2.5 Installation And Demonstration Preparation
Create or activate a Python environment with Tkinter support, then install the runtime requirements. Launching the main application without arguments opens setup. The --name option prefills a callsign, --port selects the listening TCP port, and --discovery-port selects the shared UDP discovery port. Both peers must use the same discovery port if they rely on automatic discovery. A direct connection instead requires the remote listening address and TCP port.

For one-machine testing, the two convenience launchers choose Alice on TCP 5001 and Bob on TCP 5002. Both still request a passphrase through setup. Enter the same private phrase in each window. After setup, either choose the discovered peer or connect directly to 127.0.0.1 with the other instance’s port. The local endpoint display provides a useful reference, but the loopback address is appropriate only when both processes run on the same computer.

For a classroom demonstration on two machines, launch the clients on the same permitted LAN and confirm that firewall settings allow the selected ports. Avoid simultaneously initiating the connection from both sides; one participant should connect while the other listens. Verify that the channel indicator changes only after password confirmation, exchange messages in both directions, then disconnect and reconnect. A failed discovery scan should lead to direct connection troubleshooting rather than an assumption that encryption is broken.

# CHAPTER 3: SYSTEM DESIGN
## 3.1 System Architecture
The architecture separates five responsibilities. ChatApp manages widgets, user actions, state presentation, and the event queue. SecureSession coordinates password derivation, handshake validation, readiness, and authenticated message exchange. ChatConnection handles the byte stream, framed JSON envelopes, and disconnect notification. DiscoveryService and TCPListener provide endpoint discovery and incoming connections. EncryptionManager wraps key derivation and Fernet operations, while PeerManager stores discovered endpoints.

TCP provides an ordered byte stream [11], but it does not preserve the application’s message boundaries. CLOAK therefore adds a four-byte length header before each JSON envelope. UDP is used separately for short discovery datagrams [12]. Loss of an advertisement does not corrupt an existing chat stream; later advertisements can refresh the peer entry. This separation lets discovery remain a convenience rather than a prerequisite for direct messaging.

The main data flow begins with a user action in ChatApp. A session worker opens or accepts the socket, sends its hello, and processes incoming protocol messages. Completed events are posted into the GUI queue with the originating session object. The main thread handles those events only if they still belong to the current session. This creates a clear boundary between network concurrency and widget ownership. Figure 3.1 illustrates the application modules and the two network channels.

## 3.2 Use-Case Model
The primary actor is a local chat participant. The main use cases are configuring identity, setting a passphrase, discovering peers, connecting directly, verifying the shared password, sending and receiving text, disconnecting, and closing the application. A remote participant is a cooperating actor who runs a compatible client and enters the same secret. The network is an external dependency rather than a user: its availability affects the connection use cases.

Several preconditions govern the workflow. Setup must succeed before network services begin. A connection attempt requires an offline session state. Messaging requires successful password verification. Updating the passphrase requires an inactive session so the keys cannot change underneath an established conversation. The selected callsign is a display label; it does not authorize access independently of the passphrase. A participant who knows the shared password can choose another callsign.

Failure use cases are equally important. A wrong passphrase produces a verification error. An occupied listening port produces a startup diagnostic. Invalid manual endpoints produce input feedback without opening a session. A remote departure returns the UI to an offline state. The use-case diagram presents these user goals without implying unsupported features such as registration, cloud login, file sharing, or offline delivery. This keeps the design model consistent with the implemented scope.

## 3.3 Class Model
ChatApp owns the current session, the peer registry, the listener, and discovery service. It does not directly implement cryptographic algorithms. SecureSession owns a ChatConnection and two EncryptionManager objects: one for its own advertised salt and another derived from the remote salt. This organization preserves the existing directional encryption convention while moving handshake coordination into a dedicated, GUI-independent class. It also makes secure-session behavior accessible to headless tests.

ChatConnection owns a socket, a send lock, and transport callbacks. Its send method frames a typed dictionary envelope, and its receive loop reconstructs complete frames before decoding JSON. TCPListener owns a listening socket and supplies accepted sockets to the application. DiscoveryService owns its broadcast and receive sockets and announces the configured listening endpoint. PeerManager maps endpoint identifiers to Peer objects, which retain display and freshness information.

Ownership is important to lifecycle correctness. Closing a session cancels its verification timer and closes its transport. Closing ChatApp stops the session, listener, and discovery service before destroying the Tk root. PeerManager is owned by the GUI thread rather than presented as an independently synchronized registry. Background discovery results reach that registry through queued GUI events. ## 3.4 Discovery And Peer Registry
DiscoveryService sends periodic UDP advertisements containing a discovery type, callsign, advertised TCP port, and local address metadata. The receiver uses the datagram’s source address as the peer address rather than blindly trusting the supplied address field. It validates the advertised name and port before posting a peer-found event. The combination of address and listening port identifies an endpoint, allowing two clients on the same host to appear separately.

PeerManager stores the current endpoint records. Each accepted advertisement refreshes a peer’s last-seen timestamp. A scheduled GUI task prunes peers that have stopped advertising, using the documented twelve-second freshness threshold. A peer-list refresh preserves the selected display entry when possible. The registry represents discovery freshness rather than proof of identity, password knowledge, or message-channel availability. A visible peer can still reject a TCP connection or use a different passphrase.

Discovery is deliberately optional. Broadcast support varies between networks, and Wi-Fi isolation or firewall policy may prevent advertisements from reaching another machine. The manual scan button requests a short burst of advertisements; the regular service already broadcasts every three seconds. Direct connection bypasses the discovery list entirely. If the discovery listener cannot bind, the interface reports that condition and suggests direct connection. This fallback improves usability without making an unsupported promise that every LAN will carry UDP broadcast traffic.

## 3.5 TCP Implementation And Message Framing
TCP (Transmission Control Protocol) provides a reliable, ordered, bidirectional byte stream [11]. The operating system handles TCP connection establishment, acknowledgements, retransmission, and flow control. CLOAK uses this service through Python sockets rather than implementing TCP itself. TCP carries the password-confirmation exchange and encrypted chat; UDP is used only to advertise available peers. The application can therefore connect directly even when discovery is unavailable.

In network.py, TCPListener creates an IPv4 SOCK_STREAM socket, binds it to 0.0.0.0 and the configured port, calls listen(5), and accepts connections on a background thread. Each accept returns a separate connected socket, while the listener remains available. An outgoing SecureSession uses socket.create_connection with a five-second connection timeout. Both directions then use the same ChatConnection framing and receive logic. The GUI allows only one active session; additional incoming sockets are closed while it is busy.

TCP does not preserve message boundaries: one JSON message may arrive in several reads, or adjacent messages may share a read. CLOAK prefixes each UTF-8 JSON envelope with a four-byte unsigned big-endian payload length. The receiver first reads exactly four bytes, decodes the size, and then reads exactly that many payload bytes. The _recv_exact helper loops until the requested bytes arrive or closure is detected. JSON is the envelope format [13], and its data field must be an object.

A send lock prevents concurrent writers from interleaving frames. sendall transmits the complete header and payload or raises an error. Lengths outside one byte to one MiB and malformed envelopes are rejected. Socket shutdown or an empty read ends the session and restores the GUI's offline state. TCP itself does not encrypt data; Fernet authenticates and encrypts the chat payload before transmission. A successful local write is not a remote read receipt. The tests cover fragmented frames, invalid payloads, bidirectional chat, disconnect, and reconnection.

## 3.6 Password Derivation And Encryption
EncryptionManager derives a Fernet-compatible key using PBKDF2-HMAC-SHA256. The revised implementation uses a fresh sixteen-byte random salt and 1,200,000 iterations. The salt is not a secret and is exchanged in the handshake; its purpose is to make key derivation depend on a session-specific value. PBKDF2 is a password-based derivation mechanism described in PKCS #5 [14]. Its computational work increases the cost of guessing but does not turn a weak password into a strong secret.

Fernet combines encryption and authentication within a token format [8]. The interface therefore labels it as Fernet/AES-128 rather than the earlier AES-256 label. The derived thirty-two-byte key material contains the material needed by the Fernet construction; it should not be described as a standalone AES-256 encryption key. Incoming tokens are accepted only after successful authentication and decoding. Modified ciphertext and wrong-key tokens do not become displayed plaintext.

Each peer derives its outgoing cipher from its own salt and its incoming cipher from the remote salt. This keeps the two directions explicit. Password derivation is performed in session workers rather than the GUI event loop. The work factor is fixed for protocol version 2, so both participants must use compatible code. There is no runtime negotiation of cryptographic algorithms, and the application must not silently downgrade to the earlier unverified handshake when a peer uses an old client.

## 3.7 Versioned Password-Confirmation Handshake
A new session first derives its local cipher and generates a random challenge. It sends a hello containing protocol version 2, its callsign, its salt, and its challenge. The hello is sent before the receive worker starts, preventing a local password proof from overtaking the local hello. After receiving a valid remote hello, the session derives the remote cipher using the entered password and the remote salt.

The client then encrypts a version-labeled proof binding the remote and local challenges in order. Reflected salts or challenges are rejected. When a proof comes back, the local session decrypts it using its own cipher and compares the result with the expected ordered pair of challenges. Only a matching challenge marks the session ready. The timer is cancelled and a ready event reaches the GUI. A wrong password produces an invalid proof and closes the session. An incomplete exchange times out after eight seconds once the transport handshake begins.

This exchange confirms shared-key possession for the current connection, but it is not a standardized password-authenticated key exchange. Captured material can support offline password guessing, and a person who knows the shared password can impersonate a callsign. There is no independent identity trust store. The report therefore describes the indicator as password verified, not identity verified. Fresh salts and challenges reduce accidental reuse, but they do not establish forward secrecy or conceal the handshake’s observable metadata.

## 3.8 Interface State And Event Flow
The interface has disconnected, connecting, verifying, and connected behaviors. A connection action immediately disables competing connection controls and enables cancellation. Ordinary message composition remains disabled while the socket and password verification are pending. Successful verification enables the composer and changes the channel indicators. A failure closes the session, restores direct connection, and recalculates whether the selected discovered peer can be connected.

Network workers post small events instead of accessing widgets. ChatApp polls its synchronized queue every forty milliseconds and handles at most one hundred queued events per poll. Discovery records are updated by that same GUI thread. Session events carry their source object; ChatApp discards an event if it belongs to a previous session. This prevents a late disconnect or successful-send event from damaging the state of a replacement connection.

## 3.9 Failure Handling And Resource Ownership
Connection failures occur at several layers. Manual endpoint validation rejects malformed IPv4 addresses and ports outside one to 65,535. TCP connection refusal produces a session error. A TCP listener bind failure leaves an actionable message explaining the occupied port and an alternative command-line port. The outbound path remains available if the listener cannot start. A discovery bind error is separately reported because direct TCP communication may still work.

Protocol failures are confined to the current session. Unknown message types, repeated hello messages, incompatible versions, malformed challenge fields, unexpected proof messages, invalid ciphertext, and pre-verification chat are rejected. A verification timer prevents an ordinary silent peer from leaving the GUI indefinitely in a pending state. The transport bounds the frame size before reading the full payload. These measures improve robustness but are not a complete defense against resource exhaustion on a hostile network.

Closing the application stops services and cancels scheduled Tk callbacks before destroying the window. Queued accepted sockets that were not assigned a session are closed during cleanup. The discovery service closes its receive and broadcast sockets and signals its stop event so periodic waits can end. Session close cancels its timer and closes the transport. Background threads are daemon threads, which avoids keeping the process alive after the interface exits; bounded joins and stronger cancellation could be considered in a future lifecycle refinement.

# CHAPTER 4: MODULE DESCRIPTION
## 4.1 Graphical Interface Module
The main interface is implemented in chat_app.py using Tkinter, ttk, and Canvas-based helper controls. Setup collects the callsign and passphrase before services begin. The revised startup behavior applies equally to the main entry point and the two convenience launchers. The name argument is now a convenience rather than a way to skip authentication setup. Invalid input keeps the user on the setup screen with an inline message.

The main window divides identity, encryption controls, peer access, diagnostics, and conversation content into distinct areas. The sidebar presents the local endpoint and both discovered-peer and direct-connection paths. The larger conversation area displays system feedback and messages with separate visual tags. The composer is inactive until verification completes. The minimum window size is 940 by 760, and the normal layout opens at 1100 by 820 to give the conversation more room.

The color palette uses dark panels, yellow primary actions, cyan supporting actions, green readiness, and red errors. Muted text was brightened for readability. Custom Canvas buttons support focus, Return, and Space instead of relying exclusively on mouse clicks. This is an Edgerunners-inspired presentation built from ordinary Tkinter primitives. It does not embed copyrighted character artwork or require a raster-image library at application runtime. The GUI check exercises widget state and message behavior; screenshot capture remains a separate environment-dependent operation.

## 4.2 Secure Session Module
The new session.py module makes password confirmation and chat readiness independent of Tkinter. SecureSession receives a password, callsign, event callback, and verification timeout. Its start method handles either an outgoing endpoint or an already accepted socket. The session owns its ciphers, random challenge, readiness flag, timer, and ChatConnection. This boundary lets tests construct sessions using local socket pairs without opening a window or relying on UDP discovery.

Hello validation checks protocol version, salt length, challenge shape, and callsign length. The first valid hello creates the peer cipher and triggers a proof response. Proof validation compares the decrypted result against the local challenge. Successful verification clears the session’s direct password reference, cancels the timer, and emits readiness. The application still retains the passphrase needed for future connections; Python memory management does not guarantee that secret strings are securely erased.

The send method accepts plaintext only when the session is ready and open, encrypts it with the local cipher, and delegates to the transport. Incoming chat uses the peer cipher and emits authenticated plaintext. A reentrant lock protects timer/close transitions so timeout and receive paths do not repeatedly terminate the session. Failures close transport resources and emit one session-level explanation. This module is intentionally small and explicit rather than an attempt to introduce a general-purpose secure messaging framework.
---PAGE---
## 4.3 Transport And Discovery Modules
network.py contains the low-level communication services. ChatConnection serializes envelopes, applies framing, protects sends with a lock, reads exact frame lengths, and reports messages through callbacks. TCPListener binds the configured port, accepts incoming sockets, and passes them to the application. DiscoveryService periodically announces the local listening endpoint and receives advertisements. Keeping these responsibilities separate allows a discovered endpoint and a manually entered endpoint to use the same secure-session workflow.

The revised transport rejects oversized and malformed envelopes and closes sockets on receive termination. TCP listener port reuse was tightened so a conflicting listener is reported rather than allowing ambiguous ownership of the same local listening port. Discovery advertisements retain UDP reuse behavior because multiple local clients must hear the same discovery channel. These two cases have different operational requirements and should not share an indiscriminate socket-option policy.

Discovery callbacks are delivered to ChatApp’s queue. The registry no longer mutates on the discovery thread while the GUI is listing or pruning peers. A failed discovery bind produces a user-visible fallback suggestion. Closing discovery releases its sockets and wakes periodic waits. The implementation still relies on operating-system routing and broadcast delivery. Therefore, network troubleshooting must distinguish a missing advertisement from an unreachable TCP endpoint and from a rejected password; all three can prevent chat, but each has a different cause and remedy.

## 4.4 Encryption And Peer Models
EncryptionManager remains a focused wrapper around the cryptography package. It accepts a password and an optional salt, derives the key, exposes the salt for the handshake, and provides encryption and decryption methods. The try_decrypt helper converts invalid-token outcomes to None for callers that need a simple authentication-failure result. Headless tests exercise successful shared-salt decryption, Unicode round trips, altered tokens, and incorrect passwords.

These modules illustrate the benefit of narrow interfaces. Encryption tests do not need a GUI, peer-registry behavior does not require a live socket, and the main window does not need to know the internals of PBKDF2. At the same time, abstraction does not eliminate integration obligations. A correct encryption round trip says nothing about handshake ordering or reconnect controls. The project therefore combines unit-level checks with session and desktop integration evidence instead of using one passing encryption script as proof that the complete system works.

## 4.5 Verification Method And Test Design
Verification uses the standard unittest framework [15] and a separate live Tkinter integration script. The headless suite targets behaviors with meaningful failure consequences rather than reproducing theme constants or widget construction details. Socket pairs provide deterministic byte streams for framing and secure-session tests. Local TCP sockets cover listener conflicts and refused connection attempts. A small polling helper waits for asynchronous outcomes with a bounded deadline.

The automated suite includes shared-salt Unicode encryption, tampered ciphertext, wrong passwords, fragmented frames, invalid JSON, invalid envelope shapes, oversized frames, occupied listener ports, bidirectional chat, repeated sessions, handshake timeout, and refused connections. Several scenarios are grouped within one test method, so the number of methods should not be confused with the number of exercised branches. Assertions check both successful message contents and the absence of readiness on password mismatch.

The GUI script launches two independent Tk roots, completes setup, observes discovery, connects through loopback, exchanges messages, checks composer states, disconnects, reconnects, and attempts a wrong-password session. It also checks visibility at the minimum window size. This demonstrates actual application interactions on the available machine. It does not establish a cross-platform certification or replace a two-device LAN trial. Tests and their machine-readable results are retained so the report’s results can be traced back to executable checks.

The final checks artifact records the actual headless and GUI outcomes from the available development environment. ## 4.7 User Workflow And Troubleshooting
Start both clients, enter a callsign and the same strong private passphrase, and complete setup. If the other client appears in the peer list, select it and connect from one side. Otherwise, enter the other machine’s IPv4 address and listening port in the direct field. On one computer, use 127.0.0.1 and the other instance’s distinct port. Wait for password verification before composing the first message.

If the peer list is empty, check that both applications share the discovery port and that the network permits broadcast traffic. Use direct connection to isolate discovery from TCP reachability. If TCP refuses the connection, confirm that the other client has completed setup and is listening on the expected port. If the listener reports a bind failure, close the conflicting program or restart with another --port value. A different listening port must also be used in the direct endpoint.

If password verification fails, disconnect and enter matching passphrases on both clients. Differences in capitalization and whitespace matter because the passphrase is used as entered. An old client must be updated because protocol version 2 does not silently accept the earlier handshake. If a peer closes unexpectedly, wait for the offline state, then reconnect. For submission screenshots, capture the setup screen and a verified two-way conversation manually after granting the operating system’s screen-recording permission, and avoid including real secrets.

## 4.8 Security Evaluation And Known Limits
The implementation protects message content using authenticated Fernet tokens and confirms shared-password possession before enabling chat. Fresh session salts and challenges support a predictable verification workflow. Invalid ciphertext is not displayed as a message. These are concrete implemented properties, but they do not establish independent identity verification, protection against a compromised endpoint, or secrecy after the shared password is later exposed.

The handshake is a project-specific password-confirmation exchange. It is not a PAKE and does not prevent offline guessing from captured handshake material. Strong passphrases and a suitable environment are therefore important. Callsigns and salts are not confidential, network endpoints and timing remain visible, and Fernet tokens expose a timestamp [8]. An attacker with the password can impersonate a participant. The protocol also lacks an explicit application sequence number and comprehensive replay defense within an active session.

Additional hardening would be required for hostile deployments: standardized authenticated key establishment, verified public identities, stronger resource quotas, robust idle-peer handling, replay protection, and independent review. The application is deliberately limited to one active conversation and does not maintain an identity directory or trust database. No security audit or penetration test was conducted. The appropriate conclusion is that CLOAK demonstrates password-based encrypted LAN messaging with clearer state handling, while retaining documented limitations that should guide any future extension.
